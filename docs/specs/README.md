## 運用ルール

### 命名

**ファイル名は kebab-case の物理名のみ。通し番号は付けない**（ADR `doc-naming`）。
参照するときも ``spec `prefecture-picker` `` と名前で書く。番号で呼ばない。

- frontmatter の `name` はファイル名と一致させる
- 名前を変えると参照が切れる。**一度付けた名前は変えない**
- 順序が要るときは `date` や status で表す

### 原則

- **1 機能領域 = 1 spec。** コンポーネント 1 つ = 1 spec とする。プラットフォームごとに分けない。
  4 実装が守る契約を 1 枚に書き、意図的な差異だけを「プラットフォーム差異」節に書く。
- **履歴を書かない。** 仕様が変わったら本文を「今の姿」に書き換える。
  「旧仕様は〜だった」「〜から変更」は書かない。履歴は git log / git blame が持っている。
- **spec を更新せずに振る舞いを変えない。** 実装と spec がずれた瞬間から spec は読まれなくなる。
- 新規追加のたびに、この README の一覧を更新する。

### status

| 値 | 意味 |
|---|---|
| `draft` | 起草中。**実装に入ってはいけない。** |
| `approved` | 合意済み。実装してよい。 |
| `done` | 実装完了。受け入れ条件が更新済み。 |

### platforms

frontmatter の `platforms` が、Pages サイトの対応状況マトリクスの**唯一のソース**。
別途の台帳ファイルは持たない。

| 値 | 意味 |
|---|---|
| `none` | 未着手 |
| `draft` | 実装中。公開 API は変わりうる |
| `beta` | 使えるが破壊的変更の可能性あり |
| `stable` | 公開 API 確定。破壊的変更はメジャーバージョンでのみ |

### 受け入れ条件のチェック規約

- `[x]` = 実装完了。コードで実現済みで、自動テスト・静的解析で確認できる。
- `[ ]` = 実機・実値・ネイティブ設定・生成アセット配置など、**実装後の手動確認が残る**もの。

status が `done` でも `[ ]` が残ることはある（実機確認待ちの意味）。
UI ライブラリでは実機・実ブラウザ確認が本質的に残るため、`[ ]` はむしろ通常の状態。

### テスト

テストの一覧は機能側の spec ではなく `testing.md` が持つ（作成予定）。
「何が自動テストで守られていて、何が手動確認なのか」をそこで一覧する。
