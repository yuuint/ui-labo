# Vue 版はカスタム要素を包む。作り直さない

## 背景

ADR `monorepo` は 4 実装（プレーン Web / Vue / Flutter / SwiftUI）を並べると決めている。
ADR `plain-web-custom-elements` は「CSS は共有し、**振る舞いは各実装で自然に**」と書いた。

その方針で `packages/vue` に着手したところ、`yn-prefecture-picker` は
約 420 行のうち大半が SVG の組み立て（エリアの結合、面積重心、拡大の補間、
状態の塗り分け）であることが分かった。Vue で書き直すと、この塊が 2 か所になる。

## 決定

**Vue 版は core のカスタム要素を包む薄い層とする。** 振る舞いは core にしか持たない。

`packages/vue` がやるのは 3 つだけ。

1. `v-model`（`modelValue` / `update:modelValue`）を仲介する
2. 値をプロパティとして入れる（属性は文字列しか運べない）
3. カスタム要素の登録をクライアントへ寄せ、SSR を素通りさせる

## 理由

- **二重管理を作らない。** このリポジトリは「生成は 1 か所」「spec が唯一のソース」で
  通してきた。地図の描画だけ 2 か所に置くと、修正のたびに両方へ入れる必要があり、
  片方だけ直る事故が必ず起きる。
- **利用側の設定が要らない。** レンダー関数で書くのでテンプレートコンパイラを通らず、
  `isCustomElement` の設定なしで使える。
- **SSR を通せる。** 要素の定義は `onMounted` の動的 import に寄せてあるので、
  サーバでは空の要素が出るだけ。`<client-only>` で囲む必要がない。
- Flutter / SwiftUI は包む相手が無いので、そちらは書き直しになる。
  **この ADR は Vue に限る。**

## 影響とトレードオフ

- Shadow DOM の中身はサーバで描かれない。初期表示は要素が空の状態から始まる。
  フォームの 1 項目としては許容範囲だが、地図を折り返し位置に置く画面では
  一瞬の隙間が見える。
- カスタム要素を使うので、対応ブラウザは core と同じになる。
- `value` の解釈は `codeFormat` と `selectionLevel` に依るため、
  **値は設定より後に入れる**必要がある。core の `static props` は `value` を最後に置き、
  基底クラスは定義前に渡されたプロパティをこの順で通す。
- 捨てた選択肢: Vue で書き直す。SSR で中身まで描けて Vue らしく書けるが、
  地図の描画が 2 か所になる代償が大きい。
- 捨てた選択肢: ロジックを core の `lib/` へ押し出して描画だけ Vue で書く。
  重複は減るが、押し出しの範囲が広く、先に core の大改修が必要になる。

## 再検討の条件

- SSR で中身まで描けないことが実害になった場合（初期表示の隙間が問題になる等）。
- Vue 固有の要求（scoped slot でオプションを差し替える等）が出て、
  包むだけでは表現できなくなった場合。
- core の描画部分が `lib/` へ十分に切り出され、書き直しの重複が小さくなった場合。
