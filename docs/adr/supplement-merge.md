# API が持たないフィールドはリポジトリ側で持ち、フィールド単位で所有者を分ける

## 背景

ADR `data-snapshot-from-api` で都道府県マスタを ynetlabo API から取得すると決めたが、
実際の応答を確認したところ、spec `prefecture-picker` が必要とするフィールドが 2 つ欠けていた。

| 必要なもの | API の実際 |
|---|---|
| 読み（`とうきょうと`） | フィールドが存在しない |
| 正式名称（`東京都`） | `name_jp` は `東京` のみ（短縮形） |

読みは spec `prefecture-picker` の検索機能の根幹であり、これが無いと
「とうきょう」「toukyou」での絞り込みが成立しない。

選択肢は 2 つあった。

- **(a) API 側に `kana` と正式名称を追加する。** 原本が 1 つに保たれる。
- **(b) ui-labo 側で 47 件分の補完データを持ち、API の応答と合成する。**

ADR `data-snapshot-from-api` の理由には「手書きを選ばないのは、原本が 2 つ生まれるため」と書いており、
(b) は一見それに反する。

## 決定

**(b) を採る。ただし「原本を二重化しない」は、ファイル単位ではなくフィールド単位で守る。**

どのフィールドも所有者は 1 箇所だけ。同じ値を 2 箇所に書かない。

| フィールド | 例 | 所有者 |
|---|---|---|
| `ynetlaboCode` | `"13-TOK"` | API（`pref_code`） |
| `code` | `"13"` | 導出（`pref_code` の先頭 2 桁） |
| `shortName` | `"東京"` | API（`name_jp`） |
| `romaji` | `"tokyo"` | 導出（`name` を小文字化） |
| `areaCode` | `"3-KTO"` | API（`prefarea_code`） |
| `areaName` | `"関東"` | API（`pref_area.name_jp`） |
| `name` | `"東京都"` | **リポジトリ**（補完テーブル） |
| `kana` | `"とうきょうと"` | **リポジトリ**（補完テーブル） |
| `kanaShort` | `"とうきょう"` | **リポジトリ**（補完テーブル） |
| `searchKeys` | — | 生成（上記から組み立て） |

ソースは 2 ファイル。中間の合成結果はコミットせず、生成物へ直接書き出す。

```
packages/data/src/
├── prefectures.api.json         # sync:data が書き出す。手で編集しない
└── prefectures.supplement.json  # 読み・正式名称。手で編集する
```

### 整合性の保証

合成時に以下を検査し、1 つでも満たさなければ**ビルドを失敗させる**。

1. 補完テーブルのキー集合が、API 応答の JIS コード集合と**過不足なく一致**する
2. `shortName` が `name` の前方部分になっている（`東京` ⊂ `東京都`）
3. `kanaShort` が `kana` の前方部分になっている
4. 47 件すべてが 1 つの `areaCode` に属する

## 理由

- **(a) は正しいが、ui-labo の進行を API 側の変更に縛る。**
  API は wari / mapengu / soroe が本番で使っており、
  UI ライブラリの都合でスキーマを変える判断は本来 API 側の話。
  ui-labo は最初のコンポーネントすら未実装の段階であり、
  ここで API 側の変更を待つ理由が弱い。
- **食い違いのリスクは、整合性検査で機械的に潰せる。**
  (b) の本当の危険は「API に都道府県が増減したのに補完側が古いまま」だが、
  上記の検査 1 がビルド時に必ず捕まえる。**沈黙して壊れることがない**のが要点。
- **補完するのは実質不変な値だけ。** 都道府県の読みと正式名称は変わらない。
  更新頻度が高いフィールドを手書き側に置くなら判断は変わるが、
  ここでは 47 件を一度書けば終わる。
- ADR `data-snapshot-from-api` の「原本を二重化しない」は、**同じ値が 2 箇所にあることを避ける**規範であり、
  「1 つのレコードが 2 ファイルにまたがること」を禁じてはいない。
  上表のとおり、どのフィールドも書かれている場所は 1 つだけ。

## 影響とトレードオフ

- API 側が後から `kana` を持った場合、補完テーブルとフィールドが重複する。
  そのときは所有者を API に移し、補完テーブルから削除する（値は消す、残さない）。
- 補完テーブルは人間が書くため、初回に 47 件分の読みを用意するコストがかかる。
  一度きりのコスト。
- 検査 2 / 3（前方一致）は北海道で `shortName == name` となるため、
  前方一致の定義を「等しい場合も含む」とする必要がある。
- 捨てた選択肢: 補完を各プラットフォーム実装に持たせる。
  ADR `shared-data-package` で否定済み（4 実装で同期できない）。

## 再検討の条件

- **API 側が `kana` と正式名称を持った時点で、(a) へ移行する。** これが本筋。
  移行は補完テーブルの該当フィールドを削除し、所有者表を更新するだけで済む。
- 補完テーブルのフィールドが 5 つを超えた場合。
  API との責務分担が崩れている兆候であり、どちらかに寄せる判断をし直す。
- 都道府県以外のデータで同じ補完が必要になり、
  合成ロジックがデータ種別ごとに分岐し始めた場合。
