# 4 プラットフォームを 1 リポジトリに置く

## 背景

ui-labo は同一のコンポーネントを プレーン Web / Vue / Flutter / SwiftUI の 4 実装で提供する。
配布経路は npm・pub.dev・Swift Package Manager と完全に別系統であり、
「プラットフォームごとにリポジトリを分ける」構成も成立しうる。

## 決定

`yuuint/ui-labo` 1 リポジトリに全プラットフォームを置く。`packages/` 配下に
`tokens` / `core` / `vue` / `flutter` / `swiftui` を並べ、配布はパッケージ単位で行う。

## 理由

- 4 実装が共有する資産が 2 つある — **デザイントークン**（ADR `design-token-format`）と
  **コンポーネント契約**（`docs/specs/`）。リポジトリを分けるとこの 2 つが
  サブモジュールか別パッケージ経由になり、「トークンを変えたら 4 実装を直す」という
  最も頻度の高い変更が 5 リポジトリにまたがる PR になる。
- 逆に、リポジトリを分けて得られるはずの「独立したリリースサイクル」は、
  npm / pub.dev / SPM がいずれもタグまたはパッケージ単位で解決でき、
  モノレポでも失われない。
- 実装は時間差で進む（Web → Vue → Flutter → SwiftUI）。後発の実装が
  先行実装の spec とトークンを同一リポジトリ内で参照できることの価値が大きい。

## 影響とトレードオフ

- CI が Node / Flutter / Swift の 3 ツールチェーンを要求する。
  変更に無関係なジョブを走らせないためのパス絞り込みが必須になる。
- Swift Package Manager はリポジトリのルートに `Package.swift` があることを期待する。
  `packages/swiftui/` に置く場合、利用者は SPM でサブパス指定が必要になるため、
  公開時は別リポジトリへのミラーか、ルートへの `Package.swift` 配置を検討する。
- 捨てた選択肢: プラットフォームごとの独立リポジトリ。
  共有資産の同期コストが、独立リリースの利点を上回ると判断した。

## 再検討の条件

- Swift Package Manager のサブパス配置が利用者にとって実害になった場合
  （導入手順に説明が必要になった時点で、swiftui のみ別リポジトリへ切り出す）。
- CI の実行時間が 1 変更あたり 15 分を超え、パス絞り込みでも改善しない場合。
- いずれかのプラットフォームに専任のコントリビュータが付き、
  リリース判断を独立させたくなった場合。

## 関連

- ADR `package-manager`（パッケージマネージャの選定）
