# 4 実装で共有するマスタデータは packages/data に置き、コード生成で配る

## 背景

最初のコンポーネントとして都道府県 Picker（spec `prefecture-picker`）を作るにあたり、
47 件の都道府県データ（コード・正式名称・短縮名・読み・ローマ字・地方区分）を
どこに置くかを決める必要が生じた。

このデータは「見た目」ではないため ADR `design-token-format` のデザイントークンには収まらない。
一方で、4 実装が完全に同一の値を持たなければ、同一のコンポーネントを名乗れない。
Web 版が「九州・沖縄」、Flutter 版が「九州」では利用者が混乱する。

素朴には各実装内に定数として直接書く方法があるが、
47 件 × 6 フィールド × 4 実装 = 1128 個の値を手で同期することになる。

## 決定

`packages/data` を新設する。原本は JSON 1 ファイルとし、
専用の生成スクリプトで TypeScript / Dart / Swift の型付き定数を出力する。

```
packages/data/
├── src/prefectures.json    # 原本。ここだけを編集する
├── build/                  # 生成スクリプト
└── package.json            # @ynetlabo/ui-data
```

生成物はコミットし、利用者に Node.js を要求しない（ADR `design-token-format` と同じ方針）。

## 理由

- **トークンとは変換ツールを分ける。** Style Dictionary は `$value` / `$type` を持つ
  DTCG トークンのための道具であり、マスタデータを通すのは用途外。
  無理に通すと、トークンでないものを DTCG 形式に偽装することになり、
  スキーマ検証（spec `design-tokens` の受け入れ条件）が意味を失う。
- **単純な生成なので自作コストが低い。** 入力は静的な配列 1 つ、
  出力は 3 言語の定数。テンプレート文字列で足り、外部依存を増やす必要がない。
- **将来の追加が読める。** 都道府県の次に来るのは市区町村、郵便番号、国名、通貨など、
  同じ性質（静的・多言語・4 実装共有）のデータ。1 件目で置き場所を決めておけば、
  2 件目以降は同じ型で追加できる。
- 47 件は総務省の JIS X 0401 都道府県コードで一意に定まり、
  実質的に変更されない。生成物をコミットしても陳腐化リスクが小さい。

## 影響とトレードオフ

- パッケージが 1 つ増える。ADR `package-manager`（パッケージマネージャ）の判断材料として、
  ワークスペース数が 4 → 5 になる。
- `packages/core` などが `@ynetlabo/ui-data` に依存する。
  Web 版利用者のバンドルサイズに 47 件分（およそ 4KB 未満）が乗る。
  ツリーシェイキングが効くよう、名前付きエクスポートで出力する。
- 捨てた選択肢 A: 各実装内に直書き。同期コストと不整合リスクが受け入れられない。
- 捨てた選択肢 B: Style Dictionary に相乗り。トークンの検証を汚染するため。
- 捨てた選択肢 C: 実行時に外部 API から取得。
  オフライン動作を失い、UI コンポーネントライブラリとしては不適切。

## 再検討の条件

- 生成スクリプトが 300 行を超えた、または扱うデータ種別が 5 つを超えた場合。
  汎用のコードジェネレータ（quicktype 等）の導入を検討する。
- 実行時に更新が必要なデータ（為替レート等）を扱う要件が出た場合。
  そのデータは本パッケージの対象外とし、別の仕組みを新規 ADR で決める。
- Web 版のバンドルサイズが問題になり、遅延読み込みが必要になった場合。
